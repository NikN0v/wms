## 1. Общая информация о проекте

**Тип проекта:** WMS (Warehouse Management System) — система управления складским учётом.

**Основная задача:** разработать backend для многопользовательской системы складского управления с изоляцией данных компаний.

**Среда разработки:**
- IDE: IntelliJ IDEA.
- ОС разработки: Windows.
- Локальный проект ранее находился по пути `D:\PetProjects\wms`.
- База данных PostgreSQL работает локально.
- Docker использовать не планируется.
- Исходный код и Gradle-проект необходимо считать главным источником истины при продолжении разработки.

### Бизнес-требования

Система должна развиваться поэтапно и в перспективе поддерживать:

1. Компании (тенанты), использующие систему.
2. Несколько складов у каждой компании.
3. Зоны хранения внутри складов.
4. Ячейки хранения внутри зон.
5. Каталог товаров и SKU.
6. Остатки товаров по ячейкам.
7. Приёмку товаров.
8. Резервирование остатков.
9. Задания на комплектацию заказов.
10. Отгрузку.
11. Управление статусами складских операций через State Machine.
12. Транзакционную обработку операций и блокировки при конкурентном доступе.
13. Уведомления в реальном времени через WebSocket или RSocket.
14. Интеграции с доставкой.
15. Генерацию PDF, работу со штрихкодами и QR-кодами.
16. Аутентификацию и авторизацию на основе Keycloak/OAuth2.
17. Redis и MinIO для задач, которым эти компоненты действительно потребуются.
18. OpenAPI и генерацию TypeScript-клиента.
19. Автоматизированные тесты, в том числе интеграционные тесты с Testcontainers.

Перечень описывает целевое направление развития. Эти возможности не следует считать уже реализованными.

## 3. Архитектура

Используется многослойная архитектура:

- `controller` — HTTP endpoints, извлечение параметров запроса и вызов сервисов.
- `service` — бизнес-правила, транзакции и проверки.
- `repository` — доступ к PostgreSQL через Spring Data JPA.
- `entity` — JPA-сущности.
- `dto` — входные запросы и ответы API.
- `src/main/resources/db/migration` — SQL-миграции Flyway.

Основной поток запроса:

`HTTP Controller → Service → Repository → PostgreSQL`

При возврате ответа сущность преобразуется в DTO.

В реализованных сервисах используются `@Transactional` и `@Transactional(readOnly = true)` для разделения операций записи и чтения.

### Принципы дальнейшей разработки

- Сначала изучить существующий исходный код и сохранить согласованность текущих пакетов и соглашений об именовании.
- Не переписывать работающие классы без необходимости.
- Не менять уже применённые миграции Flyway.
- Для изменений схемы создавать новые последовательные миграции.
- Проверять существование родительских объектов до создания дочерних.
- Не возвращать JPA-сущности напрямую из контроллеров.
- Не хранить складские остатки непосредственно в карточке товара.
- В дальнейшем предусмотреть корректную конкурентную обработку остатков и резервов.
- Не подключать Keycloak, Redis, MinIO и другие инфраструктурные компоненты до появления конкретной потребности.

## 4. Мультитенантность и изоляция данных

Основная модель — `Tenant`, представляющая компанию-клиента системы.

Иерархия объектов:

```text
Tenant
 ├── Warehouse
 │    └── StorageZone
 │         └── StorageLocation
 └── Product (каталог компании)
```

### Правила изоляции

1. Каждый склад принадлежит одной компании через `tenant_id`.
2. Зона хранения принадлежит конкретному складу и компании.
3. Ячейка принадлежит конкретной зоне и компании.
4. SKU уникален в пределах компании, а не всей системы.
5. Код склада уникален в пределах компании.
6. Код зоны уникален в пределах склада.
7. Код ячейки уникален в пределах зоны.
8. Сервис должен проверять принадлежность дочернего объекта соответствующему родителю.
9. PostgreSQL использует внешние ключи и составные ограничения для защиты ссылочной целостности.

На текущем этапе идентификатор компании передаётся в URL и, в некоторых запросах, в теле JSON. Контроллеры сверяют эти значения.

**Ограничение текущего этапа:** полноценная аутентификация, авторизация и защита от доступа одной компании к данным другой ещё не подтверждены. Перед эксплуатацией необходимо получать tenant-контекст из проверенной идентичности пользователя и обеспечивать изоляцию во всех операциях, а не полагаться на `tenantId` из тела запроса.

### Известные правила HTTP-ответов

- `201 Created` — успешное создание объекта.
- `200 OK` — успешное получение объекта или списка.
- `400 Bad Request` — ошибки валидации, недопустимые значения и некоторые нарушения соответствия родительских ID.
- `404 Not Found` — отсутствующая компания, склад или зона.
- `409 Conflict` — дублирующийся код компании, склада, зоны, ячейки или SKU в соответствующей области уникальности.

Ошибки в обсуждавшихся сервисах обрабатывались через `ResponseStatusException`. Наличие общего `@ControllerAdvice` в проекте не подтверждено.

- Код обрезается по краям и переводится в верхний регистр.
- Код уникален глобально.

### Склад

- `name`: обязательное, максимум 150 символов.
- `code`: обязательное, максимум 50 символов.
- Код уникален внутри компании.
- Компания должна существовать.

### Зона

- `name`: обязательное, максимум 150 символов.
- `code`: обязательное, максимум 50 символов.
- Код уникален внутри склада.
- Склад должен принадлежать указанной компании.

### Ячейка

- `code`: обязательное, максимум 50 символов.

- SKU: обязательное, максимум 100 символов.

## 8. Структура базы данных и Flyway

База данных называется `wms_db`. PostgreSQL работает локально.

Конфигурация приложения обсуждалась примерно в таком виде:

```yaml
spring:
  application:
    name: wms-backend

  datasource:
    url: ${DB_URL:jdbc:postgresql://localhost:5432/wms_db}
    username: ${DB_USERNAME:postgres}
    password: ${DB_PASSWORD}
    driver-class-name: org.postgresql.Driver

  jpa:
    hibernate:
      ddl-auto: validate
    open-in-view: false
    properties:
      hibernate:
        format_sql: true

  flyway:
    enabled: true

server:
  port: 8080
```

Фактический YAML нужно сверить с репозиторием.

`ddl-auto: validate` используется для проверки соответствия JPA-сущностей существующей схеме. Hibernate не должен автоматически создавать или изменять таблицы.

### V3 — `V3__add_type_to_storage_locations.sql`

Эта миграция была добавлена после того, как выяснилось, что в `storage_locations` отсутствует поле `type`.

Обсуждавшийся SQL:

```sql
ALTER TABLE storage_locations
    ADD COLUMN type VARCHAR(30) NOT NULL DEFAULT 'STANDARD';

ALTER TABLE storage_locations
    ADD CONSTRAINT chk_storage_locations_type
    CHECK (type IN ('STANDARD', 'RECEIVING', 'SHIPPING', 'PICKING'));
```

## 5. Мультитенантность и изоляция компаний

### 5.1. Основной принцип

Каждая компания представлена `tenant`. Данные складских операций привязаны к компании непосредственно или через связанные сущности.

Изоляция по `tenantId` — обязательное бизнес-требование.

Пользователь не должен получить доступ к данным другой компании путём изменения `tenantId` в URL, query-параметрах или теле запроса.

### 5.2. Что уже известно

- Таблица `users` содержит обязательный `tenant_id`.
- Уникальность имени пользователя обеспечивается в пределах компании.
- JWT содержит claim `tenantId`.
- `WarehouseController` использует URL вида `/api/tenants/{tenantId}/warehouses`.
- Для списка складов используется `WarehouseService.getAllByTenantId(tenantId)`.
- Для создания склада используется `WarehouseService.create(request)`.
- Ранее в `WarehouseController` проверялось совпадение `tenantId` из URL и `request.tenantId`.
- Эта проверка не обеспечивала изоляцию между компаниями: злоумышленник мог указать одинаковый ID чужой компании в URL и теле запроса.

### 5.3. Требуемые правила безопасности

Для каждого endpoint, работающего с данными компании:

1. Получать идентификатор пользователя и компании из проверенного JWT.
2. Сравнивать `tenantId` из JWT с `tenantId` из URL, если URL содержит этот параметр.
3. Не доверять `tenantId`, переданному клиентом в теле запроса.
4. Проверять принадлежность связанных сущностей той же компании.
5. Обеспечивать tenant-фильтрацию в запросах репозиториев и бизнес-операциях.
6. Не позволять изменять данные другой компании через операции обновления, удаления, перемещения, резервирования и отгрузки.
7. Проверять, что вложенные объекты — например, склад, зона, место хранения или товар — принадлежат соответствующей компании.
8. Исключить утечку данных через отчёты, поиск, пагинацию, журнал аудита и получение объектов по ID.

**Важно:** проверка только в контроллере не заменяет проверки в сервисах и запросах к БД. Для связанных сущностей нужна проверка принадлежности компании.

### 5.4. Коды ответов

Принципиально различать:

- `401 Unauthorized` — пользователь не аутентифицирован или JWT недействителен.
- `403 Forbidden` — пользователь аутентифицирован, но не имеет необходимого доступа.
- `400 Bad Request` — некорректный запрос, например противоречивые значения в URL и теле, если для данного случая выбрана такая семантика.
- `404 Not Found` — объект не существует; вопрос о применении `404` вместо `403` для чужих объектов следует решать последовательно, с учётом требований к сокрытию существования данных.

### 5.5. Текущее ограничение

### 9.2. Миграция V17

Известное содержимое миграции, создающей `users`:

```sql
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    tenant_id BIGINT NOT NULL REFERENCES tenants(id),
    username VARCHAR(100) NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    role VARCHAR(30) NOT NULL,
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT chk_users_role
        CHECK (role IN ('ADMIN', 'MANAGER', 'OPERATOR')),
    CONSTRAINT uq_users_tenant_username
        UNIQUE (tenant_id, username)
);

CREATE INDEX idx_users_tenant_id ON users (tenant_id);
```

Особенности:

- `tenant_id` ссылается на `tenants(id)`.
- `username` уникален внутри компании, а не глобально.
- Допустимые роли: `ADMIN`, `MANAGER`, `OPERATOR`.
- `is_active` по умолчанию `TRUE`.
- `created_at` устанавливается через `CURRENT_TIMESTAMP`.
- Индекс создан для `tenant_id`.

### 9.3. Остальные миграции

Известно, что история миграций начинается с `V1` и доходит как минимум до `V17`.

Содержимое `V1`–`V16` в доступном контексте полностью не представлено. Необходимо прочитать SQL-файлы миграций из:

Нельзя составлять список таблиц и колонок этих миграций по предположениям. Следует извлечь реальную структуру БД из SQL-файлов и сверить её с entity.

### 9.4. Правила работы со схемой

- Не менять применённые миграции без специальной причины.
- Новые изменения схемы оформлять следующими миграциями, начиная с номера после последней существующей.
- Проверять, что entity и PostgreSQL соответствуют друг другу.
- Проверять внешние ключи и ограничения уникальности.
- Особое внимание уделять tenant-изоляции и ссылочной целостности между компаниями, складами, товарами и операциями.

### Исправленная проблема аудита

В native SQL-запросе журнала аудита присутствовала сортировка:

```sql
ORDER BY a.created_at DESC, a.id DESC
```

Hibernate дописывал некорректную сортировку с `a.createdAt`, если `PageRequest` дополнительно содержал `Sort`. Проблему устранили, передавая `PageRequest` без дополнительного `Sort`, сохранив сортировку непосредственно в SQL.

Точное имя репозитория, метода поиска, DTO фильтров и полей аудита необходимо сверить с кодом.

## 11. Исправленные ошибки и важные решения

### 11.1. Flyway и Hibernate

- Миграции Flyway применяются к локальной PostgreSQL.
- Настройка `ddl-auto: validate` используется для проверки соответствия схемы entity.
- Проблемы предыдущих миграций были исправлены в ходе разработки; точный перечень ошибок требует проверки истории и файлов проекта.

### 11.2. Поиск по аудиту

Исправлена ошибка некорректной сортировки, возникавшая при сочетании native SQL и сортировки в `PageRequest`.

### 11.3. JWT secret

При запуске возникала ошибка:

```text
PlaceholderResolutionException:
Could not resolve placeholder 'security.jwt.secret'
```

Причина — Spring не находил свойство. Проверялась структура `application.yml`: блок `security.jwt` должен находиться на верхнем уровне, рядом с `spring`.

После исправления приложение, по сообщению пользователя, запустилось.

### 11.4. Валидация пароля

Для регистрации задан минимум 12 символов и максимум 72 символа. BCrypt используется с коэффициентом сложности `12`.

### 11.5. Ошибка с nullable-результатом BCrypt

Для результата `PasswordEncoder.encode()` использовался `requireNotNull(...)`, так как в IDE тип результата отображался как nullable.

### 11.6. JWT выдавался, но не проверялся

Сначала был реализован выпуск JWT. Затем в `SecurityConfig` подключили OAuth2 Resource Server и `JwtAuthenticationConverter`.

После этого пользователь сообщил, что проверка «вроде работает». Полный протокол отрицательных и положительных тестов в истории отсутствует.

### 11.7. Tenant-изоляция складов

Обнаружено, что сравнение `tenantId` из URL с `tenantId` из тела запроса не защищает от обращения к другой компании.

Была предложена дополнительная проверка `tenantId` по JWT в `WarehouseController`, но её применение и тестирование ещё нужно подтвердить по локальному коду.

## 13. Последний этап разработки

Последняя обсуждавшаяся задача — защита `WarehouseController` от доступа к данным другой компании.

Исходный вариант контроллера содержал:

```kotlin
@RestController
@RequestMapping("/api/tenants/{tenantId}/warehouses")
class WarehouseController(
    private val warehouseService: WarehouseService
) {
    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    fun create(
        @PathVariable tenantId: Long,
        @Valid @RequestBody request: CreateWarehouseRequest
    ): WarehouseResponse {
        if (tenantId != request.tenantId) {
            throw ResponseStatusException(
                HttpStatus.BAD_REQUEST,
                "ID компании в URL и теле запроса не совпадают"
            )
        }

        return warehouseService.create(request)
    }

    @GetMapping
    fun getAll(
        @PathVariable tenantId: Long
    ): List<WarehouseResponse> {
        return warehouseService.getAllByTenantId(tenantId)
    }
}
```

Проблема: в нём не проверялось соответствие `tenantId` из URL компании, указанной в JWT.

Был предложен вариант, в котором контроллер получает `JwtAuthenticationToken`, извлекает claim `tenantId` и проверяет соответствие перед вызовом сервиса.

Этот вариант ещё требуется сверить с текущими пакетами и применить при необходимости. Последний подтверждённый пользователем этап — получение JWT и предварительная настройка проверки JWT/ролей. Успешное тестирование обновлённого `WarehouseController` пока не подтверждено.
